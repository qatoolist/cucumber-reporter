## Fifth review response

Untyped evidence now receives structural JSON handling only when the entire body
is valid JSON. Otherwise doc strings and textual attachments use literal patterns,
even with `jsonKeys` configured. `[INFO]` logs, `{{x}}` templates, Markdown links and
timestamped logs are accepted. Explicit JSON/JSON Lines types retain malformed-input
refusal, safe evidence locations and no-output behavior.

The CLI matrix now includes 44 cases across legacy JSON and Messages, including
those untyped-text examples. Unit regressions verify that doc strings and attachments
remain byte-for-byte unchanged with key-only policies, while configured literal
patterns still mask text. Untyped malformed JSON also deliberately uses text patterns;
callers requiring structural fail-closed handling must declare the JSON type.

JSON Lines aliases (`application/jsonl`, `application/jsonlines`,
`application/x-jsonlines`, `jsonl`, `jsonlines`, `ndjson`, `text/x-ndjson`) receive
line-by-line key redaction in attachments and doc strings. `text/x-json` is treated
as JSON. JSON5 attachments receive literal-pattern scanning; structural JSON5 key
redaction remains unsupported and is documented. The fuzz check now also asserts
that arbitrary untyped evidence is not refused and valid inferred JSON stays valid.

The reported untyped-text and JSON Lines alias regressions failed before the fix
and passed afterward. Previously accepted Background/hook limitations are unchanged.
Browser, print and cross-browser CI gates remain required before tagging; none were
launched in this review response. No commit, push, tag or release was made.

Verification after this fix: `make verify` passed, including formatting, vet/lint
