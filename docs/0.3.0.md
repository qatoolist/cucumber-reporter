# 0.3.0: investigation and optional run intelligence

The single-run CLI and options version 2 remain supported. Existing plain-mode navigation IDs,
known-issue classification, generation exit codes, private output permissions,
no-network HTML, strict CSP and no-JavaScript fallback remain the defaults.
HTML bytes and the interactive layout change in this release: filters, tables, navigation,
typography, colors and JSON-tree spacing are updated. Embedded assets are larger, and
the former 400-scenario print cap is removed. References to preserving layout apply
only to compression of an already-saved PDF, not to the HTML upgrade.

## Existing workflow

```sh
cucumber-report -options options.json ./run
```

This still reads `run/cucumber.json`, creates a fresh `html-<digits>/index.html`,
and exits 0 when generation succeeds (even if tests failed).

## Optional enhanced workflow

```sh
cucumber-report -enhanced -o ./reports ./shard-a ./shard-b
cucumber-report -enhanced -run-config run.json -baseline previous/summary.json -history previous/history.json ./run
cucumber-report -enhanced -bundle -fail-on-unexpected ./run
cucumber-report -format messages ./run/cucumber.ndjson
cucumber-report -validate -strict ./run
cucumber-report -version
```

Multiple inputs require `-enhanced`. Inputs may be files or directories; directory
inputs use `cucumber.json` (`cucumber.ndjson` for Messages). Unique input basenames
identify shards; when basenames repeat, the CLI uses the shortest unique suffix of
each cleaned path, or the whole cleaned path without a leading separator when it is a
suffix of another input (`x/run.json` next to `ci/x/run.json`). The library requires a nonempty unique `Input.Name`. The output
parent must already exist. The advanced
flags also enable the enhanced workflow for a single input, except `-validate`
alone, which checks plain-mode rules.

Enhanced output includes:

- `index.html`: the offline report, with supplied analysis and retry evidence.
- `summary.json`: schema-4 current-run summary, suitable as the next baseline.
- `history.json`: a bounded array of summaries, suitable for the next run.
- `scenarios.csv`: outcomes and durations; formula-like cells are protected.
- `summary.md`: computed results and gate failures for a build summary.
- `rerun.txt`: unexpected-failure/undefined/ambiguous `feature:line` selectors.
- `attachments.json`: availability/size/type manifest for retained evidence.
- `report.zip`: when `-bundle` or configuration `bundle` is enabled, all files above
  and deduplicated attachment sidecars. Oversized binary content is included in this mode.

The enhanced writer publishes a fresh directory atomically. Exit 1 means invalid
input/configuration or an output error; exit 2 means incorrect CLI usage; exit 3
means an explicitly requested quality gate failed **after** artifacts were written.
The successful report path is printed for exit 3 too.

## Configuration example

`run.json` is separate from existing `report.Options`:

```json
{
  "id": "nightly-2026-11-06-001",
  "environment": "staging",
  "branch": "main",
  "revision": "7f3c2a91",
  "recordedAt": "2026-11-06T00:00:00Z",
  "expectedScenarios": 40,
  "expectedShards": ["shard-a", "shard-b"],
  "retain": 30,
  "gates": {
    "unexpected": true,
    "undefined": true,
    "incomplete": true,
    "newFailures": true,
    "maxRegressionPercent": 25,
    "allowFirstRun": false
  },
  "fingerprint": {
    "includeStep": true,
    "stackLines": 2,
    "patterns": ["request-id=[A-Za-z0-9-]+"]
  },
  "bundle": true
}
```

Every field is optional. Do not set an expected scenario count or shard list unless
it actually describes the run. Without an expectation, completeness is **unknown**,
not complete. A completeness gate fails on unknown or incomplete execution.

No baseline/history is needed for ordinary reports, current-run gates, merging,
redaction, exports, rerun selection or current-run attempt evidence. Comparison UI
appears only with a baseline; history appears only when supplied. A requested
comparison gate needs a usable baseline, unless `allowFirstRun` is explicitly true.
A mismatched baseline environment/branch is rejected. History from other scopes is retained in the archive but excluded from current-scope
analysis. Retention defaults to 30 runs **per environment/branch**, with a maximum
of 1,000 per scope. Archived scenarios retain only identity, status and duration;
use `summary.json`, not an archived entry, as a full baseline. Compact `history.json`
is bounded by the same 64 MiB budget as its reader. Old snapshots may be pruned
from other scopes first, with diagnostics naming the scopes. Other scopes are then
dropped largest-first before any older current-scope snapshot is pruned. If the current snapshot
alone cannot fit, `history.json` is omitted with a diagnostic. Analysis uses the
retention-only set before byte pruning, so archive size does not change the current
report's flakiness samples or known-issue observations. HTML, summary, CSV, Markdown, attachments
and the requested ZIP still publish. This applies even when no history was supplied.
Check for the archive before passing it as the next `-history` input; split large
archives by scope when needed. Baseline/history readers retain their 64 MiB limit.

Omitting `id` generates a fresh random run ID, so identical reruns remain distinct
history observations. This default is intentionally not reproducible and treats every
invocation as a new execution; rendering the same artifact twice with history counts
it twice. Set `id` to a stable CI execution ID when reprocessing artifacts or when
reproducible output is required. Use a different ID for each actual test execution.
Reusing an explicit current ID replaces that execution snapshot in the output history;
duplicate IDs within the same environment/branch in the supplied history array are rejected.
Generated run IDs are structural and marked `generatedID` in summaries; redaction
does not rewrite them. A caller run ID that changes under redaction and collides with
stored history is refused with a safe error; use a unique nonsecret execution ID.
No historic HTML files are parsed or required.

## Identity, merge and comparison rules

Plain-mode `report.ScenarioIDs` keeps its v0.2.0 behavior. Enhanced mode uses
`report.RunScenarioIDs` for annotations and metadata references. Enhanced navigation
uses the normalized full URI: a canonical root name such as `checkout.feature`
keeps `checkout-L12`, while paths, noncanonical names and non-ASCII names receive a
URI hash suffix. This prevents similarly named features from exchanging references
when shards are reordered or omitted. Positive source lines must be distinct within
a feature. Line-zero records use a name hash; indistinguishable records are refused.

Historical identity follows name collisions, with no dependence on outline keywords:

- A name unique within its feature uses normalized full URI + name. This includes
  parametrised outline rows; inserting lines above them preserves comparisons and samples.
- Colliding names use normalized full URI + name + `row` + source line. This covers
  identical-name outline rows and the same name under different `Rule:` blocks.
  The report continues and emits one diagnostic listing the navigation IDs and the
  `metadata.<navID>.identity` workaround (use the pre-redaction ID from `RunScenarioIDs`).
  Adding/removing/renaming a colliding sibling can also change the identity rule. Inserting lines above these records changes
  their identity.
- Messages builds its collision catalog from the full `gherkinDocument`, expanding
  example values into row names. A subset/rerun retains identities when the full
  document is supplied. Without that document, only available pickles can be counted.
- Legacy JSON counts the feature's elements across the supplied inputs. A subset
  containing only one of several colliding names changes that row's identity. Use
  Messages with the full document or explicit metadata to avoid that limitation.
- Explicit `metadata[scenarioNavigationID].identity` always wins. Run hooks retain
  their synthetic URI and source-line/name rule.

To pin identity across a collision-row move, scenario rename or legacy subset, use
an opaque explicit identity. Navigation references still include lines: update
annotation and metadata keys after moving source lines, even when historical
identity stays stable. Explicit identity does not relocate metadata automatically.
Normalization cleans path segments and backslashes; it does not equate absolute,
relative, `file:` or `classpath:` URIs. Use the same URI convention across runners.

Enhanced summary schema is **4**. Unsupported schemas are refused with an actionable
error. Generate enhanced annotation/metadata keys using `RunScenarioIDs`. Plain
options remain version 2 and plain navigation IDs are unchanged. `testdata/synthetic/showcase/options-enhanced.json`
is the migrated CI example; `options.json` remains the plain-mode example.
No fuzzy matching is used for CI decisions.

```json
{
  "metadata": {
    "checkout-L12": {
      "identity": "checkout.card-payment.valid",
      "worker": "worker-2",
      "started": "2026-11-06T00:00:01Z",
      "finished": "2026-11-06T00:00:04Z",
      "attempts": [
        {"number": 0, "status": "failed"},
        {"number": 1, "status": "passed"}
      ]
    }
  },
  "phases": [
    {"name": "Database setup", "worker": "setup", "started": "2026-11-06T00:00:00Z", "finished": "2026-11-06T00:00:01Z"}
  ]
}
```

Attempt numbers start at zero and are contiguous. The last status must match the
raw scenario outcome. Optional `steps` use the exported `cucumber.Step` JSON shape
and retain evidence for that attempt; Messages supplies these automatically.
Final outcomes retain the usual known-issue policy, while attempt statuses remain
raw execution statuses. Historical failure frequency reports its observed sample
count and environment/branch scope; absent history is never described as stable.
Messages run timestamps become measured run phases and, when every shard supplies
a complete interval, elapsed wall-clock time. Runner git branch/revision are displayed as facts, without populating
comparison or history scope. Only explicit configuration sets those scope fields.
Repository facts and all imported values pass through the same redaction policy.
The timeline shows real intervals and a per-worker activity/gap table when timestamps
are supplied. Gaps describe unoccupied time in the measured span, not proof that
a worker did no other work.

Inputs with the same feature URI merge their scenario lists. Conflicting feature
names/descriptions/tags are rejected. Across separate inputs, repeated source locations are always refused in v0.3.0.
The error lists the first 20 colliding URI/line locations (then "and N more") and the affected inputs. This
applies equally to CLI rendering, validation and `PrepareRun`. Disjoint shards
remain supported. Generate one report per rerun or browser/OS matrix cell, or use
the runner's `--retry` within a single input. Duplicate locations within one input
still require a recognized runner retry shape.
Consecutive Ruby executions with the same nonzero line, name and ID in one feature
are folded into retry attempts. Captured Ruby step-definition locations identify both
Background/scenario pairs and retries without Backgrounds. Other runners' duplicate
executions are not assumed to be retries. A failed attempt is rescued only by a
strictly passing final attempt; a final pending/skipped/undefined result retains the
failure. Plain reports include a flaky count. Old retry navigation slots redirect to
the final attempt instead of shifting unrelated scenario IDs.
Messages executions for the same test case are numbered by start-event arrival order;
Ruby's one-based attempt field and false retry flags do not discard retries. A final
`willBeRetried:true` with no successor still diagnoses an incomplete stream. Each attempt's details
show the runner's recorded start time, finish time and elapsed time, as recorded (time of day and
zone; the full timestamp is the `<time datetime>` value), never localised or estimated; the attempt
selector shows each start time to the millisecond. Inputs without per-attempt timestamps, such as Ruby JSON, show each attempt's summed
step time instead, labelled "no start or finish time recorded". Enhanced mode folds each standalone
`type: "background"` element's executed steps into the following scenario, retaining
failures, duration, arguments and attachments. It does not count Backgrounds as extra
scenarios or reuse a Background execution for later scenarios. Orphan Backgrounds without a following scenario retain non-passing execution in their
original navigation slot. Passing orphan Backgrounds are omitted with a numeric-location
diagnostic. A report containing only passing orphan Backgrounds says **No scenarios executed** with an informational tone. Both adapters feed one execution
step map in this order: scenario before-hooks, Background execution, each scenario
step with its before/after step hooks, then scenario after-hooks. Legacy empty or null
hook arrays are absent; real step hooks retain status, duration and evidence. Private execution metadata tracks hook/Background/own origins and scenario-owned
indices. These are renderer bookkeeping, not public fields on `cucumber.Step`. Messages resolves Background origins through pickle
step AST references to the Gherkin document; include those references when supplying
Background execution. If a document contains a Background but pickle-step AST
references are absent, a diagnostic explains that those steps count as own steps.
Legacy cucumber-js inline hooks with `hidden:true`, or an exact `Before`/`After`
keyword and no text, are hooks. Background steps inlined in cucumber-js/Godog JSON
cannot reliably be distinguished from own steps and count as own steps; use Messages
with AST references when separate Background numbering is needed.

Plain mode follows the v0.2.0 contract, with these explicit additions:

- Non-passed scenario/step hooks contribute their outcome, error and evidence.
- Standalone Background execution folds into the following scenario. Its old navigation
  ID slot stays reserved, so later IDs do not shift. An annotation on the old Background
  ID is refused with an actionable error naming the following scenario. This is an explicit compatibility change: update annotations to the final scenario ID. To target a folded Background step, use `"backgroundStep": 1` (one-based within the Background) and its `stepText`, instead of `step`. To target a scenario-owned step, retain its declared `step` number. Bookmarks on old Background or retry IDs resolve through the report’s aliases map.
- Runner `output` arrays become text attachments; cucumber-js arguments, doc-string
  media-type aliases and attachment aliases retain their evidence.
- Recognisable consecutive in-file retry attempts resolve to the final attempt.

Passing external hook rows stay hidden in plain mode, with or without a Background.
Their logs and attachments, including failure screenshots, are attached to visible
execution steps; Before-hook logs precede step evidence. Plain annotation `step` and
`outcomes[].step` use the original element's `steps[]` positions, including cucumber-js
inline hooks. They exclude external hook arrays and standalone Background steps.
That numbering never changes with a hook outcome. Enhanced mode uses scenario-owned
step numbers in both input formats and cannot annotate a hook as an own step.
Display labels and copied investigation text retain the declared number; a separate
execution position points to its row in the report. Enhanced mode displays passing
hooks too. Plain reports have no implicit gate: successful generation exits 0 even
when the displayed verdict is Failed. Enhanced annotations/metadata use enhanced
navigation IDs; plain annotations keep v0.2.0 navigation IDs.

Scenario provenance lists originating shard names. If configured expected shards are
missing, or observed scenarios are fewer than `expectedScenarios`,
unmatched static metadata entries become diagnostics and are excluded from binding;
the report remains incomplete and the completeness gate returns exit 3. Unmatched
metadata is an error without a configured missing-execution expectation. When
`expectedShards` is set, every supplied input name must be listed and expectation
names must be distinct; a list matching no supplied input is refused. Missing listed
shards remain valid completeness findings. Static annotations must
still refer to included scenarios; missing files passed as arguments remain input errors.

Same-name rows at different lines cannot reliably be distinguished from a moved
scenario duplicated across shards. Use shards from one source revision and configure
`expectedScenarios` with the `incomplete` gate to detect unexpected totals. Explicit
identities can detect duplicate executions when their source locations differ.

Comparison distinguishes new failures, fixes, added scenarios, newly skipped tests,
missing identities and longer durations. Missing does not mean deleted. A known
failure resolving an unexpected failure is a fixed *unexpected* outcome, not a clean
pass. Duration deltas compare summed steps, not wall-clock time or statistical
significance. A slowdown and its percentage gate require both outcomes to be passed,
a positive baseline duration and an increase of at least 100 ms by default.
`gates.minRegressionMs` changes the absolute floor; explicit `0` includes every
positive increase. Both the slower list and percentage gate use this same floor.
It is independent of `maxRegressionPercent`; neither gate implies statistical
significance. There is no suite-total duration gate: many increases below the per-scenario
floor may accumulate without triggering it. Use comparable environments and meaningful thresholds.

## Known-issue policies and readable banners

Existing annotations remain valid. Optional `details` contains labelled facts,
which the report renders without guessing structure from the note:

```json
{
  "scenario": "tracker-L42",
  "kind": "known",
  "ref": "KATANA-515",
  "title": "Tracker shows the wrong created quarter",
  "step": 16,
  "stepText": "the tracker rows match the expected business values",
  "observed": true,
  "details": [
    {"label": "Expected", "value": "Q4CY26"},
    {"label": "Actual", "value": "Q3CY26"},
    {"label": "Location", "value": "Google Sheets / tracker"},
    {"label": "Basis", "value": "Offer creation timestamp in UTC"}
  ],
  "note": "Additional registry context and observations remain available here."
}
```

Banners use a compact status/issue/step header, a summary, labelled detail rows,
expandable observations and notes. Long legacy notes are collapsed but preserved
verbatim. Short notes remain initially visible. The tool does not extract expected
and actual values by heuristically parsing arbitrary prose.

Optional run configuration `issues` can add `ref`, `owner`, `expires`, `reviewDate`,
`environments` and `errorPattern`. Dates are `YYYY-MM-DD`; dated policies require
`recordedAt` for deterministic evaluation. An expired exception, inapplicable
environment or nonmatching error pattern cannot cover a failure. Review dates are
informational. The original declared-step and step-text safeguards still apply.
Scoped history also highlights issues repeatedly unobserved in consecutive runs.

## Redaction

```json
{
  "redaction": {
    "patterns": ["secret-[A-Za-z0-9]+"],
    "jsonKeys": ["password", "access_token"],
    "headers": ["Authorization", "Cookie"],
    "excludeAttachments": ["credentials", "customer-export"]
  }
}
```

Redaction is explicit and off by default. All patterns match the original text;
overlapping matches are removed together, so an earlier replacement cannot truncate
a later greedy match. Existing `[REDACTED]` markers remain atomic without blocking
matches across them. Header rules mask values in line-based headers without consuming another line,
and match JSON/NDJSON key names case-insensitively. Headers in curl commands and log
prefixes and single-quoted header maps are covered. Matching uses the exact header
name: `X-Authorization` and `Proxy-Authorization` do not match `Authorization`; list
`Proxy-Authorization` separately if needed. HAR-style `{ "name": "Authorization",
"value": "..." }` pairs are not associated by header rules. Use an applicable pattern,
`jsonKeys: ["value"]` (which masks every such key), or exclude the attachment.
Malformed JSON gets best-effort quoted-header masking with a headers-only policy;
that fallback does not decode escaped JSON keys. Empty header names are refused.

Patterns scan all attachment bodies except known binary types: image/audio/video/font,
OpenXML, PDF, ZIP and common archives, octet-stream, WebAssembly, CBOR, protobuf and
legacy Word binaries. XML suffix types, including `image/svg+xml`, are text.
Doc strings are always text, even when labelled PDF, image or octet-stream; their
JSON/key rules never pass through the binary-attachment exclusion. Unknown types are scanned, including HTTP messages, CSV, PEM,
custom log types and JSON5. Invalid UTF-8 does not bypass scanning: byte-compatible
patterns still mask ASCII secrets in Latin-1 logs. This is not character-set decoding;
non-ASCII patterns must match the actual byte encoding. Non-JSON text is literal;
URL encodings and XML entities are not decoded.

JSON recognition includes Gherkin's `json` language label, `text/json`, `text/x-json`,
`application/json` and `+json` media types, case-insensitively and with optional
parameters. Nonbinary doc strings and attachments also use structural JSON redaction
when the entire body is a valid JSON object or array, regardless of type. Untyped
scalars remain text. Otherwise they use literal text patterns, so
logs such as `[INFO] ...`, templates such as `{{x}}` and Markdown links remain
accepted even with `jsonKeys` configured. This also means malformed untyped JSON
uses text patterns; declare a JSON type when structural masking must fail closed.
Non-JSON bodies use text patterns; `jsonKeys` is not a general-purpose key scanner
for arbitrary text. JSON5 supports literal-pattern scanning only;
structural JSON5 key redaction is not supported.

Valid JSON attachments/doc strings are scanned token by token, even without
`jsonKeys`: patterns cover decoded keys, decoded strings and scalar values such as
numbers. Patterns match within a single decoded token; expressions spanning JSON
syntax such as `"token"\s*:\s*"[^"]*"` do not match the serialized document. Use
`jsonKeys` for that case. Key rules inspect nested objects/arrays and mask the complete
value of matching keys. They do **not** parse JSON encoded inside a string value;
mask its outer key (for example `body`) or configure a literal secret pattern. Unchanged
spans retain key order, duplicate keys, whitespace, escape spelling and numeric
precision. A masked number becomes a JSON string containing the redaction marker.
NDJSON uses the same treatment for each line. JSON Lines aliases
`application/jsonl`, `application/jsonlines`, `application/x-jsonlines`, `jsonl`,
`jsonlines`, `ndjson` and `text/x-ndjson` share this behavior in attachments and doc strings.

When `jsonKeys` is configured, explicitly typed malformed JSON attachments, doc
strings and nonempty JSON Lines/NDJSON lines fail closed: the CLI exits 1 with a safe
error before writing HTML, sidecars, exports or `report.zip`. This also applies to retry evidence and when
literal patterns are configured alongside key rules. Repair the malformed evidence,
or explicitly exclude a malformed attachment by name before sharing the report.
Empty or JSON-whitespace-only bodies contain no values and are retained unchanged,
including empty HTTP response attachments. Blank NDJSON lines and trailing newlines
remain supported. Errors identify zero-based feature, scenario (`elements`), step,
attachment (`embeddings`) or doc-string positions, plus NDJSON line/retry indices
where applicable, without printing names or content. These positions refer to the
merged enhanced model after Background/hook folding. Library callers can identify
these evidence errors with `errors.Is(err, report.ErrRedaction)`; they are not option errors.

Without `jsonKeys`, malformed JSON falls back to literal text pattern scanning.
That fallback does not decode JSON escapes. Invalid base64 attachments still fail
inspection. Binary content is not searched for secrets: exclude attachments that
must not be shared.
Excluded attachments are absent from output. The manifest describes retained
attachments, including unavailable/invalid ones; it does not reveal excluded names.

The current model, retry evidence, HTML/fallback, sidecars and exports use the
redacted snapshot, without changing caller-owned data. Automatically derived historical
identities for the current run use redacted names/paths when redaction is enabled.
Keep redaction policy consistent across compared runs. Display metadata, workers,
caller-supplied identities, caller run IDs and environment/branch keys are masked
consistently when current input is prepared. Computed scenario/issue identities,
navigation IDs and synthetic `__run_hooks__/` URIs are structural and never pattern-masked.
Generated identities are marked `generatedIdentity`; imported generated values must
match the exact `test-` plus 32 lowercase hex digit shape. Explicit scenario and issue
identities from current input, baseline and history are all masked with the current
policy before comparison. This covers mixed-policy explicit identities. Generated
hashes cannot be reversed and rehashed under a new policy: regenerate source artifacts
with consistent policies when their underlying names or paths change under redaction.
A generated identity of a name or path that masking changed is the identity of the
masked text: a scenario whose secret changes between runs (for example `login token-1`
then `login token-2` with pattern `token-\d`) is the same scenario to the baseline,
history and the new-failures gate. The same holds for a metadata identity that a
pattern matches. The run adds an `identity` diagnostic when it compares identities
that masking changed; use opaque metadata identities that no pattern matches to tell
such scenarios apart.
Scope matching uses the masked keys; use distinct opaque nonsecret
scope identifiers so redaction cannot collapse two scopes. Structural enums, computed
reference IDs, `MimeType`, schema fields and timestamps are preserved; step,
scenario and feature keywords are display text and are masked.
Imported `recordedAt` must be RFC3339; issue observations must use recognized states,
and `counts` keys must use supported statuses with nonnegative counts. Malformed
structural values are refused without echoing their content.
Regenerate unredacted historical summaries with the same policy before sharing them.
If redaction makes identities ambiguous, supply explicit opaque identities. Selectors
whose source paths were redacted are omitted from rerun exports, with a diagnostic,
because a redacted path cannot be executed. An empty `redaction: {}` is a no-op.
Redaction is not automatic secret detection.

## Messages input and safe diagnostics

The Messages adapter supports NDJSON pickles and Gherkin locations, test cases,
scenario/step hooks, run hooks, step results, attempts, timestamps, worker IDs and
inline `IDENTITY`/`BASE64` attachments. Run hooks are explicitly labelled synthetic
execution records so a setup failure cannot disappear from the verdict. Hook records
use a hash of the logical `Input.Name` for their source URI. The CLI uses unique
input basenames, or supplied cleaned paths when basenames repeat. Keep this logical
name and within-stream hook ordering stable for history comparisons. Changing the
name changes hook identity; with repeated basenames, changing their paths can also
change it. Go callers can supply stable logical names directly. Synthetic hooks cannot take
an ordinary feature's navigation slug. Synthetic status comes from the merger's flag,
not a URI prefix. User features whose normalized URI starts with `__run_hooks__/`
are refused, including paths normalized through `./` or `..`. Reused runner IDs in different inputs do not
mix attempts: `PrepareRun` is the single owner of grouping, metadata binding and final
attempt selection. The final attempt references the scenario's evidence in HTML
instead of embedding it twice.
Run hooks remain visible as execution evidence and affect verdicts and gates, while
scenario totals and `summary.counts` exclude them. Hooks are excluded from
`expectedScenarios`; summaries separately report
`observedScenarios` and `runHooks`, and mark hook records with `runHook: true`.
Valid Messages `UNKNOWN` status is displayed as pending, with its original status in
the evidence; it is never converted to a pass. Final-run markers, referenced results and valid status/timing data
are required. External attachment URLs are rejected; the reporter never fetches
URLs or reads arbitrary paths supplied by test output. Embed evidence upstream.

The legacy parser continues ignoring unknown fields. `-validate` reports unsupported
execution-bearing fields with safe locations; `-strict` rejects these diagnostics.
Requested quality gates also apply during `-validate`: failed gates return exit 3,
while validation never writes report artifacts.
The legacy CLI now retains non-passing hooks and folds standalone Backgrounds.
Enhanced JSON loading uses feature-at-a-time
`cucumber.ParseEnhanced`, while public `Parse`, `ParseStream` and `ParseEnhanced` return concrete, source-shaped
`cucumber` models. Folding happens inside the renderer; parser results support ordinary
reflection, JSON round trips and `go-cmp` without renderer metadata. The CLI currently buffers each file and parses legacy input again for
diagnostics; the library stream parser does not make the CLI end-to-end streaming.
Empty JSON shards and completed, successful empty Messages shards are accepted; a
run containing no scenarios or hooks renders **No scenarios executed** with an informational tone. `-fail-on-unexpected` succeeds; opt into `gates.empty` to reject empty execution. Malformed JSON and unfinished Messages streams are still refused.

`-validate -enhanced` applies policies/gates but writes nothing. Consequently `-o`, `-bundle`,
`-title` and `-name` have no output effect in validation. `-fail-on-unexpected` gates
failed outcomes only; configure `gates.undefined` to include undefined/ambiguous
results. Rerun exports include those unresolved outcomes independently of gates.
CLI options files reject `analysis` and `bundleAttachments`, including null/false
values. These are Go-only output controls. `Options.Analysis` is trusted input; never decode
it from untrusted JSON. Use `PrepareRun` for computed analysis
and enhanced `-bundle` for CLI sidecars/ZIP. The Go directory writers deduplicate
content-addressed sidecars while rejecting positional filename collisions.

## UI and output scope

The report adds attention actions, denominator explanations, a compact overview,
searchable feature navigation, split failure investigation, scenario problem summaries,
search/wrap/line-number/full-screen error controls, step disclosure, image zoom/navigation,
copyable investigation summaries and optional attempt/analysis panels.

Scenario lists support an optional sortable, paginated table with column selection;
Boolean tag expressions (`and`, `or`, `not`, parentheses); multi-feature selection;
issue, evidence, change and retry filters; saved views with import/export; and filtered
CSV/rerun exports. Filters remain in the URL. A source-list URL travels with scenario
links, and same-tab scroll context is kept in session storage when available.

The Print button opens scope selection: full, summary, failures or current filtered
scenarios, with error/evidence metadata controls. Browser-native printing uses the
current print selection if one was chosen, otherwise the complete report. The former
400-scenario-per-feature cap is removed. Selected-detail reports explicitly retain
whole-run cover totals. Local report addresses require the recipient to possess a
copy of the report; they are not automatically hosted or shared.

## Compressing saved PDFs for sharing

PDF compression is separate from print scope: it keeps the saved PDF's page count,
page layout and selected report content. It does not remove passed scenarios, steps
or pages to achieve a smaller file. The existing browser Save as PDF flow is unchanged.

```sh
cucumber-report compress-pdf -quality balanced -o report-shared.pdf report.pdf
cucumber-report compress-pdf -quality small -o report-small.pdf report.pdf
cucumber-report compress-pdf -quality high -o report-high.pdf report.pdf
```

| Quality | Color/grayscale images | Intended use |
| --- | --- | --- |
| `high` | Original resolution; no downsampling | Preserve image resolution while compressing resources |
| `balanced` (default) | Downsample images above the threshold to 150 dpi | Sharing with readable screenshots |
| `small` | Downsample images above the threshold to 96 dpi | Smaller files for screen viewing |

Text and vector graphics are retained as vector content where the PDF engine supports
it; pages are not flattened into screenshots. The two sharing presets keep monochrome
images at up to 300 dpi. All presets enable stream/font compression, font subsetting
and duplicate-image detection. Higher quality does not imply that every input can be
made smaller. Image downsampling has little effect on PDFs made mostly of text/vectors.

The command prints page count, exact byte sizes and the measured reduction. It verifies
that conversion kept every page. If recompression produces a larger or equal file, it
saves an exact copy of the original instead and explicitly reports that result. There
is no promised file-size target or fixed compression ratio.

Without `-o`, the output is the input name with `.shared.pdf` replacing its extension
(for example `report.pdf` becomes `report.shared.pdf`). Existing destinations and input symlinks are
refused; the source is never overwritten. Processing is local, with private temporary
files and output permissions, no upload and a five-minute command timeout (override with `-timeout 10m`). Input size
is limited to 1 GiB. The output folder must already exist. Publication uses hard links
when supported; other filesystems use an exclusive copy that is removed on failure or
cancellation. The latter is not atomic during copying. Ctrl-C and termination signals
trigger cancellation and temporary-file cleanup; forced kills cannot run cleanup.

Encrypted and owner-password-restricted PDFs are refused rather than silently
removing their protection. Detection conservatively rejects an `/Encrypt` PDF name
(including escaped names); an unencrypted document containing that token in content
may also be refused. No password-removal or permission-changing workflow is offered.

This optional command requires **Ghostscript** (`gs` on `PATH`, or `GS` set to its
executable). On macOS install it with `brew install ghostscript`; on Ubuntu use
`sudo apt-get install ghostscript`. HTML generation and normal printing do not need it.
The Print dialog includes a **Compress a saved PDF for sharing** disclosure with preset
selection and a copyable command. It is explicit that these presets apply after saving;
an offline HTML report cannot set its browser's PDF encoding quality.

Compression uses Ghostscript's `pdfwrite` engine to rewrite the PDF. Visual report
pages are the contract; preservation of signatures, forms, accessibility tags and
other nonvisual PDF metadata is not promised. Links, outlines and tagged-PDF structure
are not covered by the current preservation tests. The `high` preset is not described as
byte-for-byte lossless. See the [Ghostscript PDF output documentation](https://ghostscript.readthedocs.io/en/latest/VectorDevices.html)
for the conversion and resource-compression behavior.

The library equivalent is `pdf.Compress(ctx, inputPath, outputPath, pdf.Options{Quality:
pdf.Balanced})`, which returns page/byte counts and whether the result is smaller.

## Library entry points

- `report.PrepareRun(inputs, options, config)` constructs a copied, classified snapshot.
- `report.WriteRunDir(prepared, parent)` writes the report and exports; the directory
  remains usable when the returned error is `report.ErrGateFailed`.
- `report.RenderTo(writer, features, options)` avoids a second complete HTML byte slice.
- `report.RenderContext` and `report.RenderToContext` accept cancellation. A streaming
  writer can contain partial bytes on cancellation; publish only after success.
- `report.RunScenarioIDs(features)` computes enhanced annotation/metadata references.
- `report.Identity(uri, component)` is the normalized URI/component hash primitive;
  `PrepareRun` chooses a unique-name, colliding-name/line or synthetic-hook component.
- `report.RerunLocations(summary, ids)` returns selectors; nil selects unexpected problems.
- `report.ValidateInput(bytes, limits)` returns safe legacy-format diagnostics. Pass
  them as `report.Input.Diagnostics` so `PrepareRun` publishes them in the summary
  and HTML report. Their text is cleaned and bounded (2 KiB each, 200 plus an
  omission notice); the reserved `runner.outcome` path and absolute filesystem
  paths return `ErrInvalidOptions`.
- `cucumber.ParseMessages(reader, limits)` preserves all execution attempts; pass
  these as `report.Input.Attempts` to `PrepareRun`.
- `cucumber.Parse(reader, limits)` reads legacy JSON and preserves supported hooks
  and explicit execution provenance. `ParseEnhanced` and `ParseStream` are deprecated
  compatibility entry points with the same contract; use `Parse` for new callers.
- Parse, then prepare: `Parse` and `ParseMessages` record a status-only audit of
  each scenario's raw results (its raw case audit) inside the parsed model. Editing
  parsed results before `PrepareRun` (for example failed to passed) does not rewrite
  that audit, so `PrepareRun` refuses a greener outcome than the raw input with
  `ErrEvidence` and names the edited scenario's URI and line. Edit the input and parse
  it again instead. Editing a `PreparedRun` (features, `Summary` or `Metadata`) is
  refused by rendering and publication as an edit after `PrepareRun`.
- Shards of one run must carry the same feature name, description and tags for a
  shared feature URI; a conflict returns `ErrInvalidInput` naming the URI and both
  inputs, and mentions mixed JSON and Messages shards only when the formats differ.

Use named fields in exported Go structs. Added optional struct fields are compatible
with named-field literals; external positional literals need updating. No external
runtime Go dependency is introduced.

## Verification

`make verify` covers format, vet, lint and race tests. The browser-tag suite covers
interaction, hostile data, attachments, print and stress. Development-only Playwright
checks in `internal/browsercheck` exercise Chromium, Firefox and WebKit, with reflow,
keyboard focus, offline requests and no-JavaScript assertions. CI runs both suites.
Goldens check the data block and no-JavaScript fallback separately as well as complete HTML.
The v0.2.0 compatibility harness checks each fixture against a per-fixture difference contract.
These checks do not constitute a complete accessibility conformance audit.

`TestReportSizeBudget` limits an attachment-free small report to 240 KB and the
5,000-step fixture to 2.5 MB. `BenchmarkRenderToLarge` and `BenchmarkPrepareRun` report
allocation/time measurements. Attachment payloads and optional history are additional.
Browser-free model/context checks (`node --test internal/browsercheck/model.test.cjs`)
exercise 20,000-scenario indexing, bounded/debounced storage and search-match contrast.
The browser harness now bounds startup to 15 seconds instead of waiting the entire
test deadline when the browser cannot launch.

## Remaining limitations and release status

The v0.3.0 tag requires the release gate and the browser, print and cross-browser CI
suites (Chromium, Firefox and WebKit) to pass on the release commit. Large CLI inputs still require whole-file
buffering and copied models. Report-generation Ctrl-C cleanup is not guaranteed;
a hidden `.html-report-*` staging directory may require removal after interruption
(PDF compression has separate cancellation cleanup). The PDF probe conservatively
refuses files that need repair. Ghostscript failures report a safe exit code and
installation/disk guidance, without quoting document content. Markdown viewers
may autolink URL-looking scenario names. Step-less Messages scenarios map to undefined;
runner-specific zero-step semantics and rerun paths with spaces are not verified for
all Cucumber implementations. Synthetic hook locations omit nonexistent line numbers in CSV and Markdown exports.
Inherited feature/scenario tags are deduplicated in summary tag arrays, preserving first occurrence order.


## Input and platform notes

UTF-8 input may begin with a BOM. Convert UTF-16 to UTF-8 first. Legacy durations
must be integer nanoseconds; behave JSON durations expressed as floating-point seconds
must be converted upstream, or use a supported Messages formatter. The behave JSON
shape itself is not accepted by the Cucumber JSON parser. Type errors identify safe
schema fields without echoing evidence. `-validate` alone checks plain rules; adding
`-enhanced` selects enhanced validation and configured gates. Validation describes
input validity separately from the scenario outcome.

The `-o` parent must already exist: create it with `mkdir -p reports` on Unix, or
`New-Item -ItemType Directory reports` in PowerShell. Missing parents produce an
output-directory error.

PDF compression searches PATH for `gs`, then `gswin64c` and `gswin32c`; an explicit
`GS` or executable option takes precedence. Ghostscript **9.50 or newer** is required.
The process's diagnostic streams are capped; report content from them is not echoed.

Print preparation builds only selected scenario details. More than 1,000 selected
scenarios requires confirmation in the report's print controls. Direct Ctrl+P for
an unconfirmed larger report prints the overview with an explicit notice explaining
how to prepare details. The cover's feature table is limited to its first 1,000
features with a visible label; totals still describe the whole run. Print scope resets
after printing or leaving the preview, so the next Ctrl+P does not reuse old filters.


Directory writers stream HTML, sync files and staging directories before publication,
and sync the parent after rename on platforms that support it. ZIP entries stream too.
The CLI warns when index.html exceeds 200 MiB. The static fallback retains all non-passed
scenario details beyond its first 1,000 scenarios, while interactive data and exports stay
complete. Ctrl+P on a large unselected report produces a cover-only document; select and
confirm Full report in the report's Print dialog for all pages. Printing or cancelling
from the preview retains the selected scope until the preview is left.

### Evidence reconciliation and runner signals

An independent scanner inventories non-passing raw results before normalization.
Parsing, folding and final rendering reconcile that inventory; missing evidence fails
closed with an explicit reporter-error diagnostic. Earlier failed retries remain in
attempt history and can only be rescued by a passing final attempt. Messages runner
failure signals override green computed headlines. Strict pending JSON runs can use
`gates.pending` and `gates.undefined`; pending beside passed is otherwise green,
while undefined is non-green. `-strict` requires `-validate` and rejects run diagnostics
as well as unsupported fields. The informational `runner.outcome` note is exempt.
Messages recovery notes for inferred retry failures or unattached Around evidence
remain strict-validation errors; the corresponding legacy JSON may not need those
notes. To render supported recovered evidence, omit `-strict` and inspect the
reported diagnostic.

Messages git facts do not implicitly set comparison/history scope. Set `branch` and
`environment` explicitly when scope separation is desired.

The captured JSON and Messages adapters agree on execution outcomes and comparison
identities. Presentation differences remain: neither adapter exposes the enclosing
Rule name; JSON preserves its runner's `Example` keyword while Messages uses `Scenario`;
logs may have `text/plain` versus `text/x.cucumber.log+plain` MIME types; Messages supplies
attempt metadata even for a single execution, while JSON supplies it only for recognized
retries. These differences do not change status, evidence contents or identity.


### Outcome, retry and evidence rules in v0.3.0

Every scenario is classified by one execution-outcome function. The page, summaries,
exports and public APIs use that classification. A separate runtime floor records
results before folding and checks each scenario: an earlier failed, undefined or
ambiguous attempt can be rescued only by a completely passing final execution.
Known issues cover only their matched step; another non-skipped failure, including
a hook or Background failure, keeps the scenario failed. Evidence in an attempt
panel cannot substitute for a correct final outcome.

Quality gates affect the displayed verdict as well as exit status. `gates.pending`,
`gates.flaky` and `gates.empty` are optional. Flaky means a passing final execution
following a non-passing attempt. `counts.flaky` is an overlapping subset, not an
additional scenario count. HTML and portable summaries include the same flaky label.
Every executed scenario has an attempt summary, including a single-attempt JSON run.
Rerun exports include pending and flaky scenarios rejected by their corresponding
gates, in addition to unresolved failure outcomes.

Ruby `around` results in legacy JSON are retained as hooks. A completed Messages case
with missing step results and an explicit failed runner result receives a failing
runner-evidence hook and a diagnostic. Ruby 9.2.1 sometimes emits only `success:false`
for an Around-after failure, with no hook result or scenario attribution. The report
preserves a failed run verdict; it cannot reconstruct the missing error or select an
accurate rerun location. An unexplained runner failure is reported explicitly.
A normal runner failure is execution data and does not invalidate `-validate -strict`.

Hook attachments carry origin names. AfterStep evidence belongs to the preceding
step. Messages hook types, when supplied, identify before/after hooks. Older Messages
streams without a hook type cannot reliably distinguish AfterStep from BeforeStep
between two steps; their generic hook labels are a documented presentation difference.

For JVM or JS JSON with ambiguous duplicate executions, prefer Messages or plain
mode. Separate rerun files and matrix cells cannot be merged in v0.3.0 when they
repeat a scenario location; generate a separate report for each run or cell.
Shard labels and ordered rerun chains are planned in the [0.3.1 roadmap](0.3.1-roadmap.md).
The reporter does not invert failure semantics for Cucumber `--wip`: a deliberately
failing WIP run can exit zero in Cucumber and still be reported as failed here.

Directory output keeps attachments exceeding a **32 MiB total encoded inline budget**
as sidecar files, including binary evidence. The per-attachment limit still applies.
`Render`/`RenderTo` cannot publish sidecars and show an explicit unavailable-content
note after that budget. Bundles include sidecars. Evidence remains available without
embedding every attachment in a very large HTML document.

`ScenarioOutcomes` returns `OutcomeFolded` for the source slots of folded Background and
retry slots, so counting non-folded outcomes does not double-count their destination.
Source-only evidence with no executed destination returns `OutcomeFolded`.
`RunStatus` has no annotation or gate parameters; it returns the shared execution
classification before those optional policies. An empty execution returns
`StatusUndefined`, while its report headline is informational. `PreparedRun` is an
snapshot with explicit public values; obtain it with `PrepareRun` and treat it as
immutable after preparation. Equal-value copies preserve rendering behavior. Its
`Equal` method compares every public field. Parsed provenance is explicit and uses
public types, so JSON copies and `go-cmp` do not depend on address-keyed caches.
`Attempt.Steps` uses the public `cucumber.Step` type.

Prepared options are bound to the matching prepared feature values. `Render`,
`RenderTo`, `Validate` and `RenderFeaturesDirTo` return `ErrInvalidOptions` when those
features differ. Prepare changed features again. `RenderDir` and `RenderDirTo` read
a source artifact and refuse prepared options; use `RenderFeaturesDirTo` with the
prepared features, or `WriteRunDir` to publish the prepared report and exports.

Parser syntax offsets are byte positions reported by the current streaming decoder.
They may differ from v0.2.0 for malformed array separators and truncated input. Valid
input behavior is unchanged by that diagnostic difference; callers should use
`errors.Is` and numeric paths instead of matching exact malformed-input byte offsets.

For bounded minifier fuzzing, use `go test ./internal/minify -run '^$' -fuzz '^FuzzJS$'
-fuzztime 30s -fuzzminimizetime 1s`, or `make fuzz-smoke`, which supplies that limit.


### Input, API and evidence details

- `Annotation.backgroundStep` targets a folded Background from its destination
  scenario ID. It is mutually exclusive with `step`, requires `stepText`, and works
  in both modes. For example: `{"scenario":"f-L9","kind":"known","title":"BUG-1",
  "backgroundStep":1,"stepText":"the shared setup fails"}`. Old Background bookmarks
  still redirect in plain mode; enhanced bookmarks use the enhanced ID scheme.
- A known issue covers earlier retry attempts only when every non-passing result
  is at the same matching declared step. An unrelated hook or step remains unexpected.
- `PreparedRun.Equal` works for values and pointers. Two preparations without a run
  ID have different generated IDs and therefore are unequal. Supply the same explicit
  execution ID for deterministic preparation and idempotent history ingestion.
- Summary schema remains **4**. Optional empty `completeness`, `computed` and
  `verdictSource` properties may be omitted; consumers must accept their absence.
- Empty execution is represented by `StatusUndefined` in the existing status API and
  by “No scenarios executed” with informational tone in the report. The `empty` gate
  can make it a failed quality gate. An empty execution never gets an OK tone.
- Ruby may omit an Around-after failure from a Messages attempt's step results.
  A fully passing attempt followed by a retry is conservatively recorded as an
  unattributed failed attempt with a diagnostic. Case-scoped Around attachments are
  retained; a stale step reference is moved to that case with a diagnostic.
- A failing Ruby AfterAll hook with zero executed scenarios can produce JSON `[]`
  and Messages `success:true`. Neither artifact exposes that failure, so it cannot
  be inferred by the reporter. Preserve the runner's exit code in CI.
- The evidence budget limits generated HTML size, not peak memory. The review
  measured approximately 2.1 GB peak RSS for 182 MB of enhanced JSON (about 1.48 GB
  for Messages). Allow memory for decoded evidence, preparation and exports.
- Scenario Expand all / Collapse all controls cover step details, errors, evidence,
  tables, doc strings, annotation notes and execution-attempt details. In-page step
  links work again when clicked repeatedly; View evidence opens and focuses its
  attachment. Collapsed attachments are removed from keyboard navigation.


Publication flushes use a bounded queue (at most 65 queued/in-progress file handles,
plus the active HTML writer). Every flush and close must complete successfully before
publication. On macOS, each file is synchronized to the storage device, followed by
one full drive-cache flush through the directory sync before rename; the parent
is synchronized afterward. This batches the full flush without publishing an
unflushed report. The release benchmark retains its 2× write-only budget.


### Runner evidence limits and input boundaries (round 16)

Cucumber Ruby 9.2.1 can write complete JSON and Messages with `success:true`
before an `AfterAll` hook fails. This affects passing and retried suites as well
as zero-scenario runs. Neither artifact contains the later failure. Keep the
runner exit status separately in CI; reporter success must not erase it:

```sh
runner_status=0
cucumber --format json --out cucumber.json || runner_status=$?
report_status=0
cucumber-report -enhanced -fail-on-unexpected -o reports cucumber.json || report_status=$?
if [ "$runner_status" -ne 0 ]; then exit "$runner_status"; fi
exit "$report_status"
```

Legacy JSON also omits `--wip`, strict and strict-flaky policy. Set explicit gates
when those policies should apply to JSON. A `--wip` run that intentionally expects
failures is still shown as failed when its evidence contains failures; the reporter
does not invert failure semantics. Messages runner failure signals remain effective
when the stream contains pending/undefined, rescued flaky attempts, missing hook
results or no attributable failure. A strictly passed retry does not explain a
`success:false` signal in the presence of those causes.

Only a final strictly passed execution rescues an earlier failure. Ruby's
`retryfinal` progress summary says “1 failed, 2 flaky”, but its failing-scenario
list names two scenarios: the failed-to-pending and failed-to-skipped cases. The
report therefore has two failed scenarios and one passed scenario. The
failed-to-`skip_this_scenario` capture similarly remains failed, even though Ruby
can exit zero. These exact differences are pinned in the corpus gate.

Ruby Messages can omit the result of an Around hook that runs after its scenario.
The report retains the runner failure at run level when the artifact cannot
attribute it to a scenario; it does not invent which passing scenario failed.
The corpus gate pins both the run failure and the available per-scenario counts.

Shard URIs must use identical spelling for the same source file. Case, URI schemes,
percent encoding, trailing whitespace and absolute versus relative paths are not
interchangeable. File-name comparisons remain case-sensitive to avoid combining
different files on case-sensitive systems. A hand-concatenated legacy JSON artifact
that exactly matches Ruby's in-file retry shape cannot be distinguished from a real
`--retry` run. Supply original artifacts separately to trigger the cross-input
refusal; do not hand-merge independent runs or matrix cells.

Rule names are not separately presented in v0.3.0. Scenario source locations and
names remain visible; Rule-level presentation is outside this frozen release scope.
